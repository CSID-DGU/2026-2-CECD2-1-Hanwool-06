# 상수도 대화 에이전트

로그인한 화면 오른쪽 아래의 원형 버튼으로 채팅창을 엽니다. 데스크톱에서는 화면의 절반 정도를 차지하는 작은 창이며, 닫았다 다시 열어도 대화가 이어집니다. `새 대화`는 문맥을 초기화합니다. 로그아웃하면 화면의 대화가 지워집니다.

Enter나 전송 버튼으로 질문을 보내면 입력칸은 즉시 비워지고 질문이 대화에 표시됩니다. 답변을 기다리는 동안 다음 질문을 입력할 수 있으며, 답변이 도착해도 작성 중인 글은 유지됩니다. 전송에 실패하면 입력칸이 비어 있을 때만 원래 질문을 복구합니다. `다시 시도`는 실패한 질문을 다시 보내고 새로 작성한 질문은 보존합니다. 한국어 조합 중 Enter는 전송하지 않으며, Shift+Enter는 줄바꿈합니다.

예를 들어 `2026년 9월 20일 역삼역 상태 알려줘`로 조회한 다음 `전날은?`, `지난주와 비교해 줘`, `왜 사용량이 많아?`처럼 질문할 수 있습니다. 답변 아래에는 실제로 조회한 근거가 표시되고, 역 자료의 링크를 누르면 해당 계량기·날짜의 상세 화면으로 이동합니다.

`최근 이상이 있었어?`처럼 최근 기록의 날짜를 생략하면 원격 자료의 최신 날짜까지 7일을 조회합니다. `오늘까지`처럼 날짜를 명시하면 요청한 날짜를 사용하고, 그 기간에 확보된 자료 범위를 함께 설명합니다. 역이나 호선을 지정해 좁혀 볼 수 있으며, 지정하지 않으면 현재 사용자가 접근 가능한 계량기 전체가 대상입니다.

## 호출 흐름

1. `POST /api/chat`이 로그인·CSRF·입력 길이를 확인합니다.
2. 서버에 저장된 대화에서 해당 사용자의 이전 질문과 역·날짜 문맥을 가져옵니다.
3. OpenAI Structured Outputs로 질문의 도메인과 의도를 분류합니다. 상수도 관리와 무관하면 정해진 안내를 반환하고, 정보가 모자라면 추가 질문을 합니다.
4. 관련 질문은 의도에 허용된 조회 도구만 모델에 제공합니다. 모델의 function call을 서버가 검증하고 실행한 뒤 `function_call_output`으로 결과를 돌려줍니다.
5. 모델은 조회 결과로 답변을 작성합니다. 서버는 사용한 근거 ID를 실제 조회 결과와 대조하고 상세 링크를 직접 만듭니다. 최종 답변 검증에 실패해도 확인된 조회 근거가 있으면 서버가 만든 자료 요약과 출처를 표시합니다.

GPT는 질문 해석과 설명을 담당합니다. 정상·주의·경고 판정은 저장된 모델 결과를 그대로 사용합니다. 사용량만 있고 분석 결과가 없으면 `미분석`, 검침 오류면 `자료 확인`, 관측값도 없으면 `자료 없음`으로 구분합니다. 원인 후보는 현장에서 확인된 원인과 구분합니다.

## 데이터는 NCP에서 읽습니다

새 채팅의 사용량·승하차·위험도는 NCP Object Storage의 다음 객체를 읽습니다.

```text
<접두어>/snapshot/manifest.json
<접두어>/snapshot/<manifest의 directory>/daily.json
<접두어>/snapshot/<manifest의 directory>/risk.json
<접두어>/arisu/index.json
<접두어>/rag/...
```

`arisu/index.json`은 수집 작업이 끝날 때마다 서버가 계량기별 아리수 파일(`arisu/<고객번호>.json`, `raw/remote_meter/<고객번호>/statuses.json`)을 모아 만드는 한 파일입니다. 채팅은 계량기마다 파일을 읽지 않고 이 파일 하나만 읽습니다. 버킷에는 다른 수집 파일과 같이 보관 때 올라갑니다.

`manifest.json`이 가리키는 한 버전을 사용합니다. NCP 연결이 실패했을 때 로컬 스냅샷이나 예제 값으로 답하지 않습니다. 기존 SQLite 등록부는 로그인 사용자의 사업소·계량기 접근 권한을 확인하는 데 사용합니다. 모델에는 허용된 계량기 자료만 전달합니다.

운영 서버의 대시보드는 로컬 스냅샷을 읽습니다. 버킷 보관은 08:05 모델 갱신이 끝나면 바로, 그리고 14:00에 돕니다. 그래서 갱신 직후 보관이 끝나기 전 몇 분 동안은 채팅이 화면보다 하루 늦을 수 있습니다. 요청한 날짜가 버킷 자료의 마지막 날보다 뒤면 답변의 자료 범위 안내에 그 마지막 날을 표시합니다.

## 운영 설정

기존 `OPENAI_API_KEY`, `OPENAI_MODEL`에 더해 웹 서비스의 환경 파일에 다음을 지정합니다. 값은 서버에만 보관합니다.

```dotenv
CHAT_STORAGE_BUCKET=hanwool-data
CHAT_STORAGE_PREFIX=prod
CHAT_STORAGE_ENDPOINT=https://kr.object.ncloudstorage.com
CHAT_STORAGE_REGION=kr-standard
CHAT_STORAGE_ACCESS_KEY='<읽기 권한이 있는 Access Key>'
CHAT_STORAGE_SECRET_KEY='<Secret Key>'
```

`CHAT_STORAGE_` 설정은 채팅의 읽기 전용 접속용입니다. 기존 `OBJECT_STORAGE_ENABLED`를 켤 필요가 없고, 수집 워커의 업로드 훅도 켜지지 않습니다. 전용 키가 없으면 기존 `OBJECT_STORAGE_ACCESS_KEY`, `OBJECT_STORAGE_SECRET_KEY`를 사용할 수 있습니다. 버킷과 접두어는 채팅용 설정으로 명시하세요.

의존성은 기존 Python requirements의 OpenAI SDK와 boto3를 사용합니다. 서버에서 의존성을 설치하고 프론트엔드를 빌드한 뒤 `water-monitor`를 재시작하면 새 DB 테이블은 자동으로 생성됩니다. 실제 운영 반영 절차는 [배포 안내](../deploy/README.md)를 따릅니다.

## RAG 자료

매뉴얼·확인된 사례는 버킷의 `rag/` 아래에 등록합니다. 정확한 파일 형식과 권한 메타데이터는 [RAG 자료 안내](../back/rag/README.md)를 참고하세요. 검색할 문서가 없거나 관련성이 부족하면 그 사실을 알립니다. 확인되지 않은 누수 사례를 만들어 답변하지 않습니다.

초기 구현은 별도 벡터 DB 없이 등록 문서를 관련성 기준으로 검색합니다. 모든 일별 수치를 임베딩하지 않으며, 수치는 스냅샷에서 정확히 조회합니다. 문서가 많아져 벡터 검색이 필요해지면 같은 검색 도구의 구현을 교체할 수 있습니다.

## 유지보수할 위치

| 위치 | 수정할 내용 |

| `back/api/main.py` | `/api/chat` 요청 형식·로그인 연결 |
| `back/api/db.py` | 사용자별 대화 테이블 |
| `back/rag/tools.py` | 모델에 공개하는 도구 스키마, 조회 함수, 근거 생성 |
| `back/rag/storage.py` | NCP 읽기 설정과 스냅샷 로딩 |
| `front/src/components/AgentChat.jsx` | 채팅창·입력·응답·근거 링크 |

| `front/src/pages/Detail/DetailPage.jsx` | 근거 링크의 계량기·날짜 선택 |

도구를 추가할 때는 입력 스키마, 실행 함수, 의도별 허용 목록을 함께 갱신하세요. 사업소 범위는 서버가 정하며 모델 인수로 받지 않습니다. 문서와 질문에 들어 있는 명령은 권한 검사를 변경할 수 없습니다.

대화 기록은 사용자별로 서버 DB에 보관되고 최근 4회 대화만 모델에 전달합니다. 30일 동안 사용하지 않은 대화는 다음 요청 때 정리합니다. 다른 사용자의 대화는 가져올 수 없으며, 접근 가능한 계량기가 바뀌면 이전 문맥을 다시 사용하지 않습니다.

계정당 시간당 20회, 한 요청에서 도구 호출 최대 12회·답변 생성 최대 8회로 제한합니다. 의도 분류를 포함한 처리 시간 예산은 55초입니다.

`get_station_status`는 지정한 날짜와 권한 범위 전체의 상태·사용량을 집계하고, 계량기별 상세는 최대 11건을 반환합니다. 날짜를 생략하면 선택한 범위의 원격 최신 자료일을 조회합니다.

조회 기간에는 일수 상한이 없습니다. 유효한 날짜인지, 종료일이 시작일보다 빠르지 않은지만 검사합니다. `get_station_history`는 요청한 기간과 권한 범위 전체의 저장된 사용량을 집계하고 역별 사용량 순위를 계산합니다. 시작일·종료일은 생략할 수 있습니다. 종료일을 생략하면 선택한 범위의 원격 최신 자료일을 쓰고, 시작일을 생략하면 종료일을 포함한 최근 7일을 조회합니다. 모델에 전달하는 일별 상세는 최대 4개 계량기에서 총 120행까지로 제한하며, 이 제한 때문에 전체 합계가 줄거나 긴 기간의 요청을 거절하지 않습니다. `find_anomalies`도 전체 일치 건수와 상태별 건수를 집계하고 최근 상세 11건을 반환합니다. 상세가 생략되면 `truncated`로 표시합니다. 이상 건수는 계량기·날짜별 판정 수이며 서로 다른 사고 수를 의미하지 않습니다.

`get_arisu_status`는 아리수 원격검침(실시간)의 누수위험·실시간 사용량·계량기 상태와 각 값의 기준 시각(카드 갱신 시각·마지막 검침 시각), 서버가 확인한 시각, 기간 안의 날짜별 검침 장애(통신 장애·계량기 장애)와 검침 기록이 있는 날 수를 돌려줍니다. 집계에는 누수위험별 계량기 수(0곳 포함), 상태별 역 이름(역이 150개 이하일 때), 전체 실시간 사용량 합계와 많이 쓴 계량기 5곳이 있습니다. 검침 날짜는 사용일이라(10-24 00:00 검침이 10-23 사용분) 기간을 생략하면 마지막 검침 사용일까지 7일을 봅니다. 아리수 자체 표시값이라 LightGBM 위험도와 따로 두며, 답변은 "아리수 누수위험 주의", "계량기 상태 정상"처럼 씁니다. 화면의 출처에는 인용한 아리수 출처마다 서버가 확인한 값(누수위험·계량기 상태·기준 시각, 집계의 누수위험 건수와 검침 장애 건수)이 함께 보입니다.

아리수 근거를 인용한 답의 아리수 주장은 아리수 근거로만 확인합니다. 맞으면 LightGBM 판정 검사에서 빼고, 다르거나 확인할 수 없으면 거부합니다(LightGBM 근거로 넘기지 않습니다). 기록이 없는 날을 정상으로 보지 않습니다. 어휘 규칙이라 처음 보는 표현은 맞아도 거부될 수 있으며, 그때는 한 번 고쳐 쓰고 안 되면 서버가 조회 근거로 답합니다. 틀릴 때는 거부 쪽으로 틀리게 두었습니다.
- 누수위험은 "아리수"를 붙인 표현만 아리수 주장으로 봅니다("아리수는 … 기준 누수위험 주의"도 됩니다). 화면에서 "위험도"는 LightGBM 판정이기 때문입니다.
- 주장은 원문의 그 문장 안에서 읽습니다("6.0톤"의 소수점은 문장 끝이 아닙니다). 역은 권한 범위의 역 이름을 "역"까지 쓴 경우에만 알아봅니다("상수도"는 상수역이 아닙니다). "강남구청역"과 "강남역"처럼 겹치면 긴 이름입니다.
- 주장은 바로 앞의 역(이어 쓴 목록 "동부역과 서부역"이면 모두), 없으면 주장 뒤의 역들("…안전인 역은 동부역, 서부역")을 가리킵니다. 가리킨 역마다 그 역의 아리수 값(계량기 행이나 집계의 상태별 역 이름)이 근거에 있어야 하고, 그 역의 모든 계량기가 그 값이어야 합니다. 역을 말하지 않은 주장은 인용한 모든 아리수 값에 맞아야 합니다("주의"가 섞인 집계로 "아리수 누수위험은 안전"이라고 하지 못합니다). "모두", "현재"를 붙여도 같습니다.
- 다음 주장으로 넘어가기 전(쉼표, "이며", "지만" 등 앞)에 부정("없/않/아니")이 있으면 그 값이 없어야 맞습니다. "문제가 없다", "이상 없다"는 값의 부정으로 보지 않습니다. "정상이 아닌 곳은 없습니다"처럼 부정이 둘이면 뜻이 모호해 거부합니다.
- 건수를 붙인 표현("아리수 누수위험 주의 11곳, 경고 0곳", "주의·경고 2곳")은 인용한 아리수 집계의 그 라벨 건수(여럿이면 합)와 같아야 하고, 역을 말했으면 그 역의 집계로만 확인합니다. 계량기 행만 인용했으면 건수를 확인할 수 없어 거부합니다. 라벨과 건수 사이에는 "인 계량기는" 같은 정해진 말만 옵니다. 다른 말이 끼면 그 부분은 일반 검사에 남겨, "아리수 누수위험 안전이며 경고 0건"의 "경고 0건"은 LightGBM 건수로 검사됩니다.
- "통신 장애·계량기 장애 기록은 조회되지 않았습니다", "장애 기록은 없습니다", "통신 장애가 있었던 날이 없습니다", "검침 장애 0회", "통신 오류 없음"처럼 장애가 없다는 주장은 그 역·날짜·장애 종류의 검침 장애가 인용한 근거에 없어야 합니다. 문장에 역이 없으면 같은 줄 앞의 역으로 봅니다("- 온수역: …. 같은 기간 장애 기록은 없습니다"). 상태는 띄어쓰기를 무시하고 비교하며("계량기장애"), 카드에 지금 장애로 표시된 경우도 장애로 봅니다. 장애 행이 잘린(31건 넘음) 계량기나 날짜가 없는 집계만으로는 날짜별 장애 없음을 확인할 수 없어 거부합니다. "영향을 줬는지는 확인되지 않았습니다", "없었다고 답할 수 없습니다"처럼 여부나 남의 말을 옮기는 문장은 주장으로 보지 않습니다. 아리수 근거 없이는 장애가 없다고 쓸 수 없습니다.
- 위 규칙으로 읽히지 않은 검침 "정상"("모든 계량기가 정상적으로 검침되었습니다")은 아리수 근거를 인용한 답에서 거부합니다.
- 한 답에 아리수 주장이 40개를 넘으면 비정상 답으로 보고 거부합니다(검사 시간을 묶습니다).
- "비정상", "정상이 아닌"은 아리수 표현으로 빼지 않습니다. 지시로 쓰지 않게 하고, 쓰면 LightGBM '정상' 판정처럼 검사합니다.

아리수 조회만으로 답할 수 있는 것은 질문에 아리수에만 있는 말(아리수·원격검침·실시간 사용량·통신/계량기/검침 장애)이 직접 있을 때뿐입니다. "누수 위험", "계량기 상태"처럼 LightGBM 판정으로도 읽히는 질문은 LightGBM 조회 결과를 인용해야 합니다. 이 판단은 모델이 아니라 질문 문장으로 합니다. 요청한 역(또는 전체 범위)마다 실제 LightGBM 판정(분석한 날이 있는 자료나 정상·주의·경고)을 인용했는지 따로 보며, 그런 판정이 없는 범위가 하나라도 있는 답은 분석 자료가 없는 답처럼 "이상 없음"·"정상"·"0건"을 말할 수 없습니다.

검증에 쓰는 정규식은 공백을 두 칸까지만 보고 겹치는 반복을 쓰지 않습니다. 답변은 최대 3,000자인데, 긴 공백이나 같은 판정어를 되풀이한 답이 되추적을 폭증시켜 서버를 멈추지 못하게 하려는 것입니다.

자료 확인 행에는 위험도 파일이 계산한 사유와 시작일·일수(`reason`, `data_check_since`, `data_check_days`)가 있습니다. 그래서 "계량기 값이 멈췄어? 언제부터야?"에 "원격검침 값이 2026-07-27부터 89일째 그대로"처럼 답합니다. "오늘 업무 요약"은 이상 조회로 분류하고, 최신 자료일 하루의 주의·경고·자료 확인과 아리수 집계를 함께 정리합니다.

`search_local_events`는 원인 질문에서만, 요청한 역과 날짜로 한 요청에 한 번 씁니다. 날짜는 요청한 날짜나 기간 안이어야 하고(끝이 열린 기간은 이번 조회 기준일까지), 날짜를 정하지 않은 질문은 이번 조회 기준일까지의 최근 7일(도구의 기본 기간) 안의 날짜만 쓸 수 있습니다. 검색 질문은 서버가 정합니다(그날 그 역 주변의 단수·상수도 공사·역사 공사·경기·공연·행사). 모델이 주소를 지어내지 못하게, 웹 검색이 실제로 돌려준 https 주소이고 날짜가 하루 안쪽인 사건만 출처로 남깁니다. 결과는 신뢰할 수 없는 외부 자료로 표시되어 날짜·판정의 근거가 되지 못하며, 화면에서는 웹 출처만 따로 새 창으로 엽니다. 검색 뒤에도 답을 쓰고 한 번 고쳐 쓸 시간(20초)을 남기도록, 남은 시간이 30초보다 적으면 검색하지 않고 검색은 최대 18초에서 끊습니다.

최종 답변이 검증을 통과하지 못하고 질문에 맞는 근거가 이미 전달됐으면, 서버가 실패 이유를 한 번 알려 주고 다시 쓰게 합니다. 다시 쓴 답도 같은 검증을 거치며, 또 실패하면 이전처럼 서버가 만든 자료 요약과 출처를 표시합니다. 마지막 답변 생성 차례에는 다시 쓰지 않고 바로 자료 요약을 표시합니다.

답변 아래의 자료 범위 안내는 같은 범위(역, 역이 없으면 호선이나 전체)에서 더 넓은 기간의 안내에 들어가는 안내를 한 번만 씁니다. 요청 기간의 날짜가 모두 있고 일부 계량기만 빠진 날이 있으면 "전체 요청 기간의 집계가 아니며" 대신 빠진 계량기-사용일 수를 알립니다.

집계에는 요청 기간과 실제 사용량·분석 자료의 보유 기간, 유효 자료 수와 누락 자료 수를 함께 담습니다. 예를 들어 2025년부터 오늘까지를 물었더라도 분석 결과가 일부 날짜에만 있으면 그 범위에서 확인된 주의·경고 횟수로 설명해야 합니다. 자료가 없는 날짜는 정상이나 0회로 간주하지 않습니다. 결측과 자료 확인 항목은 사용량 합계에서 제외하며, 주간 비교는 최근 7일과 직전 7일에 유효한 관측값이 모두 있을 때 증감을 계산합니다.
